# spec: roadmap — `homelib_rag.roadmap`

**Implemented by:** WP-14 · **Consumed by:** `homelib_rag.agent` (`build_roadmap` tool), `apps/api` (`POST /v1/roadmap`).
**v2:** product §8 splits this into `POST /v1/mentor/intake` (proposal) and
`POST /v1/paths` (accepted artifact). Keep this module until WP06; do not
ship both `/v1/roadmap` and `/v1/paths` as two sources of truth in OpenAPI.

## Purpose

Turn a user's stated interests, level, and goal into a personalized, ordered
reading roadmap over the Open Library catalog corpus (`data/catalog.jsonl` /
the `catalog` table — never the banned Kaggle set, §4.2). Output is a typed,
validated schema — `RoadmapResponse`/`RoadmapStep` as defined in
`specs/api.md`; this spec does not redefine those fields. Parsing is
fail-closed: exactly one bounded repair retry on a schema/parse failure, then
a hard error — a half-parsed roadmap is never returned. The per-step `why`
rationale is generated by the LLM at answer time; any `description` shipped
on a `CatalogEntry` (`specs/core-models.md`) is optional prompt context only,
never our product copy, because Open Library description fields have mixed
per-record provenance (§4.2).

## Public interface

```python
def build_roadmap(
    interests: list[str],
    level: Level,                 # "beginner"|"intermediate"|"advanced" — specs/api.md RoadmapRequest.level
    goal: str,
    max_steps: int = 8,
    *,
    client: OpenAICompatibleClient,
    catalog: CatalogSearch,        # homelib_rag.index catalog search, same corpus as search_catalog
) -> RoadmapResponse               # specs/api.md — request_id, steps: list[RoadmapStep], rationale

class RoadmapParseError(Exception): ...

def _parse_and_validate(raw: str, candidates: list[CatalogEntry]) -> RoadmapResponse   # raises RoadmapParseError
def _repair_prompt(raw: str, validation_error: str) -> str
```

## Data contracts (field-level)

`RoadmapResponse`, `RoadmapStep` — defined in `specs/api.md`; not redefined
here. `CatalogEntry` — defined in `specs/core-models.md`; not redefined here.

Contract added by this spec, on top of the field list in `specs/api.md`:

```
candidates     list[CatalogEntry]     # retrieved via catalog search for this
                                       # request; the only books the LLM may
                                       # cite into RoadmapStep

RoadmapStep.ol_key   when not None, MUST equal the ol_key of one of
                     `candidates` — the model may never invent a book absent
                     from what it was actually given
RoadmapStep.why      free text generated by the LLM; MUST NOT be reproduced
                     verbatim from CatalogEntry.description (that field is
                     optional context, never output copy)
len(steps)          <= max_steps, always — even if the model proposes more
```

## Error and degradation behavior

- **Repair protocol:** call LLM → parse JSON → Pydantic-validate against
  `RoadmapResponse`. On `JSONDecodeError` or `ValidationError`, build one
  repair prompt containing the raw output plus the validation error text and
  make exactly one more LLM call. If the second attempt also fails to
  parse/validate, raise `RoadmapParseError` — never return a partially
  populated `RoadmapResponse`. `apps/api`'s `/v1/roadmap` handler maps
  `RoadmapParseError` to an `HTTPException(502, ...)` (`{detail: str}`
  envelope per `specs/api.md`); this is a distinct failure mode from
  `/v1/ask`'s `degraded: true` path because `RoadmapResponse` carries no
  `degraded` field.
- **Connectivity failures bypass the repair loop.** `LLMUnreachableError`
  (endpoint down/timeout) propagates immediately without consuming the one
  repair attempt — retrying the same call will not fix an unreachable
  endpoint, so the repair budget is reserved for parse/validation failures.
- **Invented candidates:** if `_parse_and_validate` finds a step whose
  `ol_key` is not in `candidates`, that counts as a validation failure and
  follows the same repair-then-hard-error path above.
- **Over-length output:** if the model proposes more than `max_steps` steps,
  `_parse_and_validate` truncates deterministically to the first `max_steps`
  by `order` rather than treating it as a parse failure — the cap is
  enforced by the parser, not by hoping the prompt is obeyed.

## Named red tests

- `test_roadmap_schema_fail_closed` — a fake LLM returns invalid JSON on both
  the first call and the repair call; assert `RoadmapParseError` is raised
  and no `RoadmapResponse` object is ever returned.
- `test_roadmap_schema_repairs_on_second_attempt` — first call malformed,
  repair call valid; assert a valid `RoadmapResponse` is returned and the
  repair prompt sent on the second call contains the validation error text
  from the first.
- `test_roadmap_steps_reference_only_retrieved_candidates` — assert no
  returned step's `ol_key` falls outside the `candidates` set passed in for
  that request (invented-book guard).
- `test_roadmap_max_steps_bounded` — a fake LLM proposes more steps than
  `max_steps`; assert `len(result.steps) <= max_steps`.
